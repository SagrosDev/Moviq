# Story 1.11: Enforce the Password and Credential Policy

Status: done

## Story

As an account holder,
I want strong but usable password controls,
so that my credential is protected without arbitrary composition rules.

## Acceptance Criteria

1. **Given** registration, password reset, or authenticated password change
   **When** a password shorter than 15 characters, longer than 128 characters, or present in the approved weak/compromised blocklist is submitted
   **Then** the server rejects it with a localized corrective message that does not echo the password
   **And** no credential or partial account change is persisted.

2. **Given** a 15-128 character passphrase containing spaces or supported Unicode
   **When** it is pasted, autofilled, generated by a password manager, or entered with the optional reveal control
   **Then** the UI and server accept it without requiring uppercase, lowercase, digit, or symbol combinations
   **And** the reveal control exposes an accessible pressed state.

3. **Given** an accepted password
   **When** it is stored or a periodic-change policy is evaluated
   **Then** only Django's approved salted password hash is persisted, readable credentials never enter API responses, audit, or logs, and no periodic change is required without compromise evidence or an authorized reset
   **And** automated tests inspect persistence and redacted telemetry.

### Story intent

- Story 1.11 is the shared password-policy foundation for the first auth capabilities. It must land before Story 1.12 registration, Story 1.14 sign-in/out, Story 2.2 authenticated password change, and Story 1.16 forgot-password recovery so those stories all consume the same validated credential rules.
- On Tuesday, August 4, 2026, the repo still has no public registration, sign-in, password-reset, or change-password UI/API flow implemented. This story should therefore establish the reusable backend policy, validation contracts, localized copy, and shared frontend password-input behavior that later auth stories plug into rather than inventing four different password implementations.

### Epic and cross-story context

- Epic 1 is building the thin end-to-end journey from landing through registration, sign-in, workflow creation, and first process execution. Story 1.11 is the credential-policy slice that must be in place before account onboarding and recovery become safe to expose.
- Story 1.9 already enforced the single-Organization identity boundary. Password policy must preserve that non-disclosing posture: credential validation failures cannot reveal whether an account or Organization already exists.
- Story 1.10 already established transactional command/idempotency and redacted operational telemetry. Password-related writes and failures must inherit those patterns instead of introducing bespoke logging or unsafe debug output.

### Previous story intelligence

- Story 1.10 also documented the current health/UAT/security posture as synthetic-only on August 4, 2026. Do not expand scope into MFA, passkeys, SSO, or production-only breach integrations; those remain outside the approved MVP.
- The current implementation artifacts continue to prefer safe, non-disclosing Problem Details and redaction tests over informal conventions. Password policy must extend those tests, not bypass them.

### Latest technical notes

- The local architecture spine still pins Django `5.2.15` as the approved stack version, but Django's official documentation on Tuesday, August 4, 2026 also lists `5.2.16` release notes. No story-driven framework upgrade is required here; use the approved local stack and only rely on validator/hash APIs that are stable across current Django 5.2 patch releases.
- Django 5.2's password-management documentation states that Django stores passwords with salted hashes, uses PBKDF2 by default, and supports stronger alternatives such as Argon2 if explicitly configured. Keep Moviqo on Django-approved hashers only.
- Django 5.2 also documents that password validators are applied by password forms and management commands, not automatically at the model level. That means future registration/reset/change flows must call `validate_password()` or an equivalent shared seam before `create_user()`/`set_password()` persistence.
- Current NIST password guidance and OWASP's Authentication Cheat Sheet align with this story's acceptance criteria: allow long passphrases, spaces, and Unicode; avoid arbitrary composition rules; use blocklists for common/compromised values; and do not force periodic password rotation without compromise evidence.
