# Repository Agent Instructions

## Frontend

- Functions in `Moviqo.Front/src/**/*.{ts,tsx}` and frontend tests/build scripts should be declared as arrow function constants, for example `export const HomePage = () => { ... };` or `const normalizeValue = (value: string) => { ... };`.
- Avoid `function` declarations for new frontend implementation code unless TypeScript/framework constraints require them, such as overload signatures or intentionally hoisted declarations.

### Frontend UI implementation

- Use pinned Tailwind CSS through the Vite plugin as the default styling foundation for new and redesigned frontend surfaces. Map approved Moviqo tokens through Tailwind theme variables; do not introduce raw component-level hex colors, arbitrary spacing scales, or dynamically constructed Tailwind class fragments.
- Use React Router for application routing, nested public/authenticated layouts, route parameters, and canonical deep links. Do not extend the current pathname-comparison router or append a major editor below an unrelated creation/dashboard page.
- Use TanStack Query for server-owned catalog and read-model state, keyed by Organization/resource/route identity with deliberate invalidation. Keep unsaved Workflow/Form documents, revision conflicts, explicit Save Draft orchestration, and transient selection in focused feature reducers; do not copy editor documents into global Context or a second server-state cache.
- Pages and features must compose approved source-owned primitives from `Moviqo.Front/src/shared/ui` when one exists. Native `input`, `select`, `textarea`, and `button` elements belong inside those primitives; do not create a new page-specific control merely by attaching an unrelated global CSS class.
- The shared UI layer must provide consistent domain-free page shells, headers, containers, cards, buttons, form fields, inputs, selects, password fields, form sections, action bars, alerts, badges, and Form Grid primitives. Add accessible headless primitives only for complex interactions such as dialogs, popovers, or comboboxes.
- Use the pinned `@xyflow/react` package for the Workflow Editor canvas. React Flow owns only canvas interaction and presentation (nodes, edges, selection, position, pan, zoom, and connection gestures); the Moviqo workflow document, reducer, revision tokens, explicit save, conflicts, validation, assignments, and publication remain authoritative. Adapt between those models explicitly and retain keyboard-accessible non-drag operations.
- Do not place the domain-aware Task Form renderer or Form Designer in `shared/ui`. Keep generic controls and the twelve-column Form Grid in `shared/ui`, the runtime `TaskFormRenderer` and typed field registry in `features/task-form`, the Workflow canvas in `features/workflow-design`, and the dedicated Form Designer in `features/form-design`. Both editors consume the same revisioned Workflow/Form entity contracts; neither feature may deep-import the other or create a competing document model.
- Use a pinned stable dnd-kit package set as the Form Designer drag/drop and sortable interaction adapter. It may own pointer/keyboard gesture state only; the Moviqo Form document, reducer, stable IDs, revisions, validation, and save behavior remain authoritative. Every drag operation also needs discoverable click/double-click and explicit keyboard controls. Do not introduce Form.io, SurveyJS Creator, JSON Forms, RJSF, or another general form-builder model without an approved architecture change.
- Do not introduce React Hook Form, Formik, or a second general form-state system without an approved architecture change. Static forms use the shared controls with focused local state; dynamic Workflow and Task Forms preserve the existing explicit reducers, generated API contracts, revision tokens, and server-authoritative validation.
- Desktop Forms use the approved twelve-column grid and explicit field spans. Supported narrow layouts reflow into one readable column without horizontal loss of operation. Authentication forms use compact content widths, registration uses structured onboarding sections, and authoring uses a dedicated wide workspace.
- Use one primary action per region. Back/cancel actions are secondary, destructive actions are separated and confirmed where required, and routine save or Task completion must not gain unnecessary confirmation.
- All Moviqo-owned visible copy must come from the localization catalog, use correct Spanish spelling and accents, and receive English review. Never ship translation keys, developer placeholders, raw provider messages, or implementation terminology as user-facing content.
- Before applying a new palette broadly, render representative real components and states on the Design System page, capture desktop and mobile screenshots, and obtain human visual approval. Automated contrast checks remain required but do not substitute for visual review.
- Preserve semantic HTML, visible focus, label and error association, keyboard operation, reduced motion, non-color-only state, and practical 44 CSS-pixel targets. A visually improved component is not complete if it weakens accessibility or backend authority.
- On failed form submission, show a localized error summary with actionable field labels, focus the summary, scroll/focus the first invalid field, and provide a visible form-level explanation for errors that do not map to a rendered control. Preserve correctable values, clear each field error when corrected, and keep correlation IDs secondary to recovery guidance.

## UAT Backend Deployment

- The actual public UAT application and deployed-journey base URL is `https://moviqo-uat-synthetic.web.app`. Use it for `MOVIQO_E2E_BASE_URL`, public UAT health checks, and other instructions that require the browser-facing UAT origin.
- Some repository deployment-contract files still contain the older `https://uat.moviqo.internal` value. Treat that value as stale rather than as the live UAT host. Reconcile contract, Cloud Run environment, allowed-host, CSRF-origin, and public-app-base-URL values intentionally in a reviewed change; do not silently change live deployment settings.
- The UAT Cloud Run backend is continuously deployed from the connected GitHub repository through its existing Google Cloud Build trigger. A normal backend release starts by merging or pushing to the configured deployment branch; Google Cloud builds the container image, pushes it, and deploys the Cloud Run revision.
- Preserve this established GitHub-to-Cloud-Run workflow. Do not tell the user to perform a separate local Docker or `gcloud builds submit` build, image push, or manual service deployment unless the user explicitly requests a manual recovery procedure or the existing continuous-deployment trigger is unavailable.
- The backend container currently starts Gunicorn directly; the repository Dockerfile does not run Django migrations. Never assume that the GitHub-connected Cloud Run deployment applies migrations automatically.
- The existing dedicated Cloud Run migration job is named `moviqo-back-uat-migrate`. Reuse and update that job for backend migrations; do not create a duplicate migration job.
- The email-delivery Cloud Run job `moviqo-uat-outbox-drain` is deployed in `us-east1`. Cloud Scheduler job `moviqo-uat-outbox-drain-every-minute` invokes it every minute through OAuth. Confirm both the Scheduler attempt and the resulting Cloud Run Job execution succeed; a Scheduler HTTP 200 proves only that execution was accepted.
- The existing UAT job/Scheduler service account is `moviqo-uat-runner@moviqo-uat-synthetic.iam.gserviceaccount.com` (the console display name may differ). It has Cloud Run Invoker for scheduled execution. Do not substitute the nonexistent `moviqo-uat-jobs@moviqo-uat-synthetic.iam.gserviceaccount.com` identity or the default Compute Engine service account.
- Moviqo owns `mymoviqo.com`. Cloudflare manages its DNS, and Resend has verified the sending subdomain `updates.mymoviqo.com`. Backend and outbox-job runtimes must set the non-secret sender contract `MOVIQO_RESEND_FROM_EMAIL=Moviqo <notifications@updates.mymoviqo.com>`; do not use `onboarding@resend.dev` or a `moviqo.local` sender.
- `moviqo-uat-outbox-drain` injects the Resend API key from Secret Manager secret `moviqo-uat-resend-api-key`. It also injects `MOVIQO_RESEND_TEST_RECIPIENT` from `moviqo-uat-resend-test-recipient` only to route the deployed journey's reserved `@synthetic.moviqo.test` identity to a deliverable test mailbox. Never request, commit, or log either secret value. Normal UAT registrations and invitations preserve and deliver to the real address entered by the user.
- For a release containing Django migrations, first inspect the migration operations and the existing Cloud Build trigger. Prefer adding execution of `moviqo-back-uat-migrate` to the established Cloud Build release path, using the exact image built for the commit, the migration service account, and the migration database credential. Do not introduce a second, unrelated deployment process.
- Order automated releases as: build the commit image, run its required migrations successfully, deploy that exact image to Cloud Run, verify `/api/v1/health/start/` reports the expected build and `synthetic-only`, and only then run the deployed journey.
- The `deployed-journey` test must target the exact deployed commit. Do not treat a run that races the Cloud Run deployment as a valid release result; trigger or rerun it only after the matching revision is ready.
- Repository deployment contracts describe required UAT configuration but do not prove that external Google Cloud trigger settings perform a step. Clearly distinguish repository evidence from settings that must be verified in the Google Cloud console.
